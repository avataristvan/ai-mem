# CLAUDE.md

Agent-facing supplement to README.md. Dev commands and critical contributor gotchas.

## Dev Commands

```bash
pip install -e .            # editable install (no ML, no BM25)
pip install -e ".[hybrid]"  # with BM25 hybrid search
pip install -e ".[dream]"   # with Anthropic SDK for mem-dream
pip install -e ".[config]"  # with pyyaml for agents.yaml support
python3 -m ai_mem.server    # run MCP server directly
python3 install.py          # register with Claude Code / Gemini CLI / Cursor
python3 uninstall.py        # remove all integration artifacts (preserves data)
python3 -m ai_mem.hook          # run SessionStart hook manually
python3 -m ai_mem.posttool_hook # run PostToolUse hook manually (pipe JSON payload on stdin)
python -m pytest tests/ -v  # run tests
mem-dream --dry-run         # preview entries without API calls
mem-dream --mode hier       # consolidate all collections (hier = default)
mem-dream --expert          # consolidate all subagent.* collections with expert focus hint
```

## Critical Invariants

Things that will bite you in the first hour:

- Tests that call `upsert` directly must include non-empty metadata (ChromaDB rejects empty dicts). Use `AddMemoryUseCase` in tests — it always injects timestamps.
- `posttool_hook.py` imports `GLOBAL_COLLECTION` and `detect_repo_context` at **module level** (not lazily inside `main()`) so tests can patch them via `patch.object`. Hooks that use lazy imports inside `main()` are not patchable at module scope. (`WORKSPACE_COLLECTION` was imported here too until the `ctx.has_claude_md` gate fix removed the need for it — removing an import that's dead in source but still referenced by a test's `patch.object(module, "WORKSPACE_COLLECTION", ...)` breaks that test with `AttributeError`, so check test-side patch targets too before dropping an import.)
- `mem_delete` with no `ids` drops the **entire collection**; repo signals this by returning `-1`.
- `QueryMemoryUseCase` takes only `(repo, track_access)` — no ranker, no build_features.
- **FIXED 2026-07-31 (was: scores were not cosine similarity, and thresholds were structurally unable to filter the top hit).** `ChromaMemoryRepository.query()` used to compute `score = 1.0 - dist`, but collections are created via `get_or_create_collection(name)` with no explicit space, which defaults to `l2` (verified live: `col.configuration_json` reports `{'hnsw': {'space': 'l2', ...}}`). Empirically confirmed (real embeddings, known cosine similarity 0.1208): Chroma's returned `dist` for that pair was 1.7583488, exactly `2 - 2*cos_sim` (squared L2 on normalized embeddings) — not `sqrt(2-2*cos_sim)` (plain L2). So the correct relationship is `dist = 2 - 2*cos_sim`, i.e. `cos_sim = 1 - dist/2`, not `1 - dist`. Combined with `BM25MemoryRepository._normalize`'s min-max rescaling of *both* fusion components (which always maps the best-of-pool candidate to exactly 1.0 regardless of absolute quality), the fused top hit was mathematically guaranteed to clear any threshold ≤ `alpha` — not a calibration problem, a proof. **Resolution** (migration-free, no re-embedding, no collection recreation — only the score *interpretation* changed):
  1. `chroma_repository.py::query()` now computes `score=round(1.0 - dist / 2.0, 4)`.
  2. `bm25_repository.py`'s fusion no longer min-max-normalizes the cosine component — only BM25's genuinely unbounded raw score gets rescaled; `fused = alpha * cosine_raw + (1-alpha) * bm25_norm`. **Residual fixed 2026-07-31 (later same day):** BM25's own min-max normalization (`_normalize`) still floored irrelevant top-hits at roughly 0.45–0.60 (same bug class, one layer further down). Replaced `_normalize` (deleted) with `_saturate(scores) = [s / (s + _BM25_SATURATION_K) for s in scores]`, `_BM25_SATURATION_K = 2.0` (empirically derived from the live-DB median nonzero raw BM25 score, ~1.6 — see ai-mem entry `bm25_saturating_transform_research_decision_2026_07_31` for the full derivation and rejected alternatives: RRF, theoretical-max-BM25, z-score/CombSUM/MNZ). Same fix shape as the cosine-side fix: an absolute, pool-independent transform (depends only on the candidate's own raw score) instead of a pool-relative rescale. `docs/hybrid-search.md` updated to match; `TorchMicroRanker` reference removed from its pipeline diagram (that ranker was already gone from the code, the doc just hadn't caught up). Threshold recalibration in the bullet below is **not yet done** — the fused-score distribution has shifted again and `CONTEXT_MIN_SCORE`/`ANTIPATTERN_MIN_SCORE`/`DILEMMA_MIN_SCORE` still reflect the pre-saturation distribution; re-measure against the live DB before trusting them (rough estimate from the research entry: likely lands near 0.38–0.41, but must be re-measured, not assumed).
  3. `userprompt_hook.py`'s thresholds were recalibrated against real measurements on the live production DB (see next bullet) rather than guessed.
- `userprompt_hook.py` context injection fires whenever a result score ≥ `CONTEXT_MIN_SCORE = 0.62` (raised from the pre-fix 0.3 on 2026-07-31; `ANTIPATTERN_MIN_SCORE`/`DILEMMA_MIN_SCORE = 0.58`, raised from 0.4). These were measured empirically against `~/.local/share/ai-mem`'s real `global`/`repo.ai-mem` collections post-fix: irrelevant prompts topped out around 0.60 (0.55 for the smaller anti-pattern-filtered pool), relevant ones started around 0.58–0.71 depending on collection homogeneity — thresholds sit just above the measured noise ceiling, favoring precision over recall since the old threshold injected near-unconditionally. Re-measure if BM25's residual min-max flooring (above) is ever fixed, since that will lower the noise ceiling and may allow a lower, more permissive threshold. The query text is still the raw current-turn prompt only (`payload.get("prompt", "")`) — no conversation history, no active-task context — so a two-word confirmation ("ja, ablegen") once scored 1.00 pre-fix against a completely unrelated entry. `MIN_QUERY_CHARS = 15` (added 2026-07-31, character count not word count — language-independent) skips the query entirely below that length as a separate, complementary guard.
- `_hook_deps.py` exposes `_build_query_uc(db_path, with_bm25)` — the single assembly point for hooks. `posttool_hook` passes `with_bm25=False`; `userprompt_hook` passes `True`.
- The ML ranker (`TorchMicroRanker`, `RankerRegistry`) was removed in 2026-06. No `[ml]` extra or `torch` dependency remains.
- `[always-present]` gate requires `confidence > 0.9` AND `access_count ≥ 3` AND `boost_count ≥ 1`. Entries without an explicit `/reflect` boost never qualify — regardless of age or access count. Existing high-value entries from before the confidence system need a one-time `mem_boost` to re-qualify. Until 2026-07-31 this gate only ever scanned `ctx.collection` (the repo-scoped collection) — never `GLOBAL_COLLECTION` — so a high-confidence `global` entry was never surfaced at SessionStart regardless of access_count, only reachable via `userprompt_hook`'s unreliable per-message query. **Fixed**: `hook.py` now also calls `_high_confidence_entries(repo, GLOBAL_COLLECTION, ..., max_count=_HIGH_CONFIDENCE_GLOBAL_MAX)` unconditionally (not gated on `ctx.has_claude_md` — global applies everywhere), rendered as a separate `[always-present: global]` block. `_HIGH_CONFIDENCE_GLOBAL_MAX = 2` is a distinct, smaller cap from the repo-scoped `_HIGH_CONFIDENCE_MAX = 3` — a full repo-scoped pool must never crowd out global entries or vice versa, and the cap stays fixed regardless of how large either collection grows (same fixed-cap-not-dump discipline as everywhere else in the hook system; see `pattern_injection_caps_not_dumps` in repo.ai-mem's own memory). Anything that must never be silently missed still belongs in CLAUDE.md over `global` when in doubt, since CLAUDE.md has no cap at all — it loads in full every session.
- `dream_memory._confidence_report`'s promotion-candidate list (`confidence > 0.9 AND access_count ≥ 3`) is purely deterministic — it has no memory of past `mem-dream` runs, so a high-confidence entry the user deliberately decided to *keep* in ai-mem (rather than promote to CLAUDE.md) gets re-proposed on every subsequent run. Set `keep_in_ai_mem: true` in the entry's metadata (`mem_add` with the same `documents`/`ids`, just the new metadata field — merge semantics in `AddMemoryUseCase` preserve everything else) to suppress it from the promotion list permanently; it still shows up under Decay Candidates if confidence later drops, since that check is unaffected.
- `mem_move` (`MoveMemoryUseCase` in `application/move_memory.py`) moves entries between collections by reading via `get_by_ids`, writing via `upsert`, then `delete`-ing the confirmed subset from the source — it deliberately bypasses `AddMemoryUseCase` (whose "preserve prior metadata" merge only looks within the same collection it's writing to, which would wrongly reset confidence/access_count on a cross-collection move). Same pattern as `split_memory.py`. If an id already exists at the target with different text, it's skipped and reported as a `MoveConflict` rather than overwritten; identical text at the target is a no-op merge (still moved). `from_collection == to_collection` raises `ValueError` (caught in `server.py`, returned as `Error: ...`) instead of silently deleting entries via a no-op upsert+delete round trip. Duplicate ids in the request are deduped up front. An empty `ids` list short-circuits to an empty `MoveResult` before any repo call — `get_by_ids([])` itself raises inside ChromaDB, and even if it didn't, `repo.delete(collection, [])` would drop the entire collection. Known v1 limitation: edges only reference `target_id`, no collection field, so other entries in the source collection that referenced a moved entry become dangling — not fixed, no reverse-edge index exists.
- `detect_repo_context()` (`ai_mem/repo_context.py`) checks `AI_MEM_WORKSPACE_ROOT` **before** the git-based fallback. When set, the collection scope is derived from the CLAUDE.md directory's path relative to that root (sanitized, dot-joined), not from `git remote`/`git rev-parse` — so two different repos under the same workspace root can never collide with git-derived names, but `RepoContext.git_root` is left `None` in this path (not computed, since git isn't consulted). If the CLAUDE.md directory falls outside the workspace root, it falls through to the normal git-based detection instead of erroring. `install.py` sets this var interactively at install time (prompt is skippable). Since hook subprocesses don't inherit the `env` block set on the MCP server entry in `~/.claude.json` (same caveat as `AI_MEM_PATH` — see the `pattern_blindtest_methodik` entry in ai-mem's own memory), `register_claude` also prefixes the four hook commands (`hook_cmd`/`userprompt_cmd`/`pretool_cmd`/`posttool_cmd`) with `AI_MEM_WORKSPACE_ROOT=<path> ` so hooks and the MCP server agree on collection naming. Because that changes the exact command string, hook dedup on re-install matches by module name (`_upsert_hook_command`, `-m <module>` substring) and updates the existing entry in place instead of exact string equality — otherwise re-running install after setting a workspace root would register a second, duplicate hook alongside the old unprefixed one.
- **`WORKSPACE_COLLECTION` is not a catch-all for "not yet configured" project dirs.** If a directory has its own `CLAUDE.md` but is outside `AI_MEM_WORKSPACE_ROOT` (or the var is unset) *and* isn't a git repo, `detect_repo_context` scopes it by its own directory name (`repo.<dirname>`, sanitized) rather than falling back to `WORKSPACE_COLLECTION` — mirrors the existing git-repo-without-a-remote fallback (`repo.<git_root.name>`) one level earlier. Fixed 2026-07-31 after a context audit found the old fallback dumping unrelated projects' entries into the shared `workspace` collection, which then surfaced as noisy, off-topic hits in `userprompt_hook`'s injected context (scores 0.6–0.9 but no real relevance to the prompt). `WORKSPACE_COLLECTION` is now reserved for the true no-`CLAUDE.md`-anywhere case and the case where `CLAUDE.md` sits directly at the workspace root itself.
